Contributing

Kept in sync with CONTRIBUTING.md in the repository · the repository file is the authoritative source

Thank you for your interest in EasySSH! EasySSH is a portable Windows SSH/SFTP terminal (Rust + Tauri 2 + WebView2 + russh + xterm.js, built entirely from open-source components) with 100% original code.

# How to File an Issue

  1. Search existing issues before filing a new one to avoid duplicates.
  2. Please include the following information:
    • The EasySSH version (visible in the title bar, e.g. 2.3.2)
    • Your Windows version and architecture (e.g. Windows 11 x64)
    • Reproduction steps and the expected/actual behavior
    • Relevant error messages (connection failure notices, snippets from the %TEMP%\easyssh-debug.log debug log, etc.)
  3. Security vulnerabilities should not be reported publicly through issues — please read SECURITY.

# How to Submit a Pull Request

  1. Fork the repository and create a feature branch (e.g. feat/sftp-drag-upload).
  2. Keep changes focused: one PR solves one problem.
  3. Verify locally before submitting: run npm start and manually test the core flows (connection, SFTP, settings).
  4. Do not modify deployment artifacts outside the application code (never commit the contents of the release/ or dist/ directories directly).
  5. If a change affects user-visible functionality, you must update the README "Version History" section accordingly (see "Release Process" below).

# Setting Up the Development Environment

Node.js ≥ 18 on a Windows x64 machine (the build output is a portable Windows app).

git clone <repository URL>
cd EasySSH
npm install
npm start            # Run locally for debugging
npm run build:exe    # Build the single-file portable release/EasySSH-<version>.exe
npm run package:win  # Fallback: electron-packager folder output to dist/

# Code Style

  • JavaScript follows the existing style: 2-space indentation, single quotes, semicolons; stay consistent with the current main.js / preload.js / renderer.js.
  • Main process (main.js) and renderer process (renderer.js) have clearly separated responsibilities; IPC goes through the controlled interfaces exposed by preload.js.
  • Any new third-party dependency must be an open-source component, and its purpose must be documented in the README/docs.
  • User-facing messages are written in Chinese; code comments are written in Chinese.
  • No external network requests (zero-CDN principle).

# Commit Message Conventions

Use the type: summary format; the summary is written in Chinese and states the change in one sentence. Common type prefixes:

  • feat: new feature (e.g. feat: SFTP 支持文本转换传输模式)
  • fix: bug fix (e.g. fix: 修复 PKCS#8 私钥无法解析的问题)
  • docs: documentation changes · style: styling/UI adjustments · refactor: refactoring · chore: builds, dependencies and other chores

# Release Process (Important)

Every new release must follow all of these steps:

  1. Update the version number: edit the version field in package.json (the artifact filename is generated by electron-builder from ${version}).
  2. Update the README "Version History": add a ### v<version> (<date>) entry listing every addition and fix. The README is the authoritative source for version history.
  3. Build the artifacts: npm run build:exe produces release/EasySSH-<version>.exe; npm run package:win produces the folder version (used for the zip extract-and-run edition). Artifact filenames must include the version number.
  4. Commit and tag: commit the README history, the package.json version bump, and the artifacts together; a v<version> tag is recommended.
  5. Automatic website sync: tools/sync.js automatically parses README history entries, scans artifacts, verifies sha256, then copies them and regenerates site-data.json — the website shows new versions with no manual intervention.
  6. CHANGELOG.md is generated from the README history (the README is the authoritative source).

Note on the v5 branch: the v5-line source code lives on the repository's v5-dev branch (Rust + Tauri 2 architecture). Its development environment requires the Rust stable toolchain and Windows 10/11 x64; build with cargo build --release (in the src-tauri directory). Target the main branch for PRs; releases are executed by the maintainers following the smoke-test gate process.
