# 方案文档：客户端统计 与 官网访客统计 的归因关联

> 状态：待评审（本文档为执行依据）
> 撰写：2026-11-15
> 目标会话：另起会话专门执行本方案，执行前通读本文，按「执行顺序」一节推进
> 项目：EasySSH 官网（EasySSH/site-server，发布机 la.trae.show:4685）+ EasySSH v5 客户端（EasySSH，Rust + Tauri 2）

## 1. 背景与目标

当前官网有两条完全独立的数据链：

- **访客统计**（`api/visit/track.php`）：页脚打点记录 {完整来源URL(rf)、IP、UA、访问页面、时间}，来源含 github/gitee/搜索引擎/直接访问等
- **客户端统计**（`api/stats/report.php`）：客户端携带匿名ID(anonId) 上报 {版本、操作系统、CPU、内存、磁盘、显卡、地域…}，服务端按设备档案聚合

**目标**：建立"哪次官网访问 → 哪次下载 → 哪个客户端安装/运行 → 提交了哪些动态"的相互关联：

1. 设备档案可展示：来自哪次访问、来源是什么链接（GitHub 仓库 / Gitee 仓库 / 搜索引擎 / 直接访问 / 其他）
2. 动态记录（最近提交动态）行尾显示来源徽章，点击可见完整来源 URL 与对应那次访问的详情
3. 访客统计侧反向标注：哪次访问产生了哪个设备
4. 新增「来源分布 TOP5」看板卡片

## 2. 现状与关键事实（执行会话必须先核实的约束）

- 客户端为**绿色版单文件 portable exe**（Tauri 2），无安装过程
- 客户端本地生成 anonId（sha256 截断 hex，16-64 位），首次上报建立设备档案
- 客户端每次启动会调用 `api/update/check` 检查升级（`api/update/check` 为普通 HTTP 端点，升级包走加密通道）
- 上报去抖：同设备 12h 内静默去重；跨 24h 重复上报计入流水
- 访客流水 v5.1.5 起记录完整来源链接（rf 字段）；admin.html 已排除在打点之外
- 服务端 `st_apply_region` 用完整 IP 解析归属地并缓存（`stats-geocache.json`，按 IP 前缀）
- 相关安全机制不可破坏：update-keys 签名链、ticket 不涉及升级包加解密、上报信封 AES-GCM + HMAC 时效签名

## 3. 方案 A：下载票据归因（主方案，分服务端票 + 客户端终身携带两层）

### 3.1 核心机制（适配绿色版，无安装器）

绿色版 exe 无法携带 URL 参数，也没有安装器写配置。因此票据的分发与携带分两层：

**第一层（纯服务端，零客户端改动即可用）**：
- 用户点击官网下载按钮 → JS 先请求 `api/download/ticket.php` → 服务端签发票据并记录
  `{tok(随机32字节hex), visitId(访客流水ID), referrer(完整来源URL), src(分类), ip(完整IP), ts, attributed:[]}`，票据保留 90 天；归因匹配窗默认 7 天（可配置）；一票最多归因 10 台设备
- 随后触发 exe 下载（URL 可带 `?t=tok` 仅作对时参考，客户端不解析）
- `report.php` 收到**新设备首次上报**时：在票据表中找「IP 相同 + 时间在 [首报时间-匹配窗(默认7天,可配置), 首报时间] 内 + 未消费且未超多设备上限(10台)」的最近一张票 → 命中则归因并消费；未命中 → 走方案 B 或标 unknown

**第二层（客户端改动，票据终身携带，推荐随下个版本发版）**：
- 客户端首次启动调用 `api/update/check` 时，服务端按 IP+时间窗匹配到未消费票据后，**在 check 响应 JSON 中附带 `download_ticket: tok` 字段**（老客户端不认识该字段，自动忽略，完全兼容）
- 客户端把 tok **持久化写入本地配置**（configstate），**终身携带**：此后每次统计上报都附带 `tok`
- 服务端收益：
  - 归因不再依赖首报时刻的 IP 匹配（下载在网络 A、首次运行在网络 B 也能通过 check 响应下发 tok）
  - 设备档案先写入 `origin`，之后每次上报带 tok 可**重复校验/重新归因**（用户清档重装生成新 anonId 时，凭 tok 重新挂到同一次下载与访问）
  - 票据消费时机改为"首次被客户端确认携带"，防重放（票据表记录 consumed）

**追溯归因（retroactive attribution，二期规则，覆盖"所有版本永久携带"）**：
- 载体分工：老版本客户端代码不可变，其"永久携带"由**服务端设备档案承担**（origin 一旦写入终身跟随该设备）；客户端本地 tok 只负责"档案丢失后重新对账"（清档/重装/换 anonId）与跨网络精确归因，仅新版代码可拥有
- 规则：设备升级到带 tok 能力的版本后启动 → `update/check` 时服务端发现该设备 `origin.src == "unknown"` → 按 **firstSeen 的 IP + 时间窗回查历史票据**（保留期内）：
  - 命中未消费/未超上限票据 → **补发 tok + 服务端直接把 origin 从 unknown 补成精确归因**（`via:"ticket"`，`attributedAt` 记补归因时间，`retroactive:true`）
  - 超票据保留期 → 尝试方案 B 访客流水启发式补标（`via:"heuristic"`，疑似）
- tok 绑定与重放：tok 与 anonId 首次上报绑定后锁定；同 tok 后续上报只能匹配已绑定 anonId。复制 exe 的多设备走票据 `attributed` 数组（一票多 anonId，上限 10 台），两套机制分开
- 覆盖范围诚实说明：追溯归因只惠及"近期下载、之后才升级"的设备（受票据 90 天保留期与访客流水 1000 条限制）；`firstSeen` 超期的老设备只能 B 启发式；永不升级的设备依赖首报时的服务端归因，档案在则终身有效，清档重装后仅 B 启发式
- PE overlay 打标（每次下载生成内嵌 tok 的 exe 副本）：只能覆盖部署后的新下载（存量文件无法回溯打标；老版本代码不读 overlay），与 update/check 下发 tok 价值重叠，维持二期可选、不排期

### 3.2 来源分类规则

| 分类 | 判定（按下载点击时访客流水的 rf 来源URL） |
|---|---|
| github | 域名含 github.com（可细分仓库页/Release 页） |
| gitee | 域名含 gitee.com |
| search | bing/google/baidu/duckduckgo 等搜索引擎域名 |
| direct | 无 referrer（直接访问/收藏夹/客户端内置下载） |
| other | 其余外部链接（保留完整 URL 展示） |
| app-update | （预留）设备产生于应用内升级渠道而非官网访问 |
| unknown | 无票据且启发式未命中 |

### 3.3 数据模型变更

**新增** `data/stats-tickets.json`（webroot 之外，与 stats-db.json 同目录策略）：
```json
{ "tickets": { "<tok>": { "visitId": "...", "src": "github", "url": "https://github.com/...",
    "ip": "x.x.x.x", "ts": 1790000000000, "expire": 1790086400000, "consumed": false } }, "meta": {...} }
```
上限保护与原子写参照 `stats-ratelimit.json` 的既有做法（条数上限 + LOCK_EX + rename）。

**stats-db.json** `clients[anonId]` 增加可选字段（不进上报字段白名单，仅服务端写入）：
```json
"origin": { "src": "github", "url": "https://github.com/EasySSHCN/easyssh", "visitId": "v-...",
            "tok": "...", "downloadAt": 1790000000000, "attributedAt": 1790001000000, "via": "ticket"|"heuristic" }
```

**api 改动**：
- 新增 `api/download/ticket.php`（POST/GET 均可，写票据；不鉴权，频控参照 captcha 的每 IP 滑窗）
- `api/update/check`：响应可选附带 `download_ticket`（对 IP+时间窗命中的未消费票据；**不动签名与升级包链路**）
- `api/stats/report.php`：解密后若载荷含 `tok` → 校验并归因/重归因；新设备无 tok → IP+时间窗票据匹配 → 方案 B 兜底
- `api/stats/admin.php`：`summary` 聚合新增 `bySrc`；`list/device/log` 行附带 origin；新增可选动作 `visit_link`（按 visitId 查访客流水）

### 3.4 后台展示（admin.html）

- 动态记录行尾来源徽章：`🔗 GitHub` / `🔗 Gitee` / `🔗 直接访问` / `🔗 其他`（点击弹窗：完整来源 URL + 该次访问的页面/IP/UA/时间）
- 设备详细记录卡片新增「来源归因」区块：来源分类 → 完整 URL(可点击) → 访客流水ID → 下载时间 → 归因方式(ticket/heuristic)
- 访客统计流水条目反向标注：该次访问的下载票据已被消费 → 显示「→ 已产生设备 <anonId 前12位>」点击打开该设备记录（复用 recModal）
- 新增「来源分布 TOP5」卡片（bySrc 聚合，台数链接复用 recModal，新增 bucket `bySrc`）

### 3.5 客户端改动（EasySSH，量小）

1. `updater.rs`/`updater.js` 相关：解析 update/check 响应中的 `download_ticket`，存在则写入本地配置持久化
2. `stats.rs`：上报载荷附带持久化的 `tok`（无则为空/缺省，服务端兼容）
3. 不改升级包加解密、不改 anonId 生成、不改 UI
4. 发版协调：随下个版本发布；老版本行为完全不变

### 3.6 隐私说明

- 票据是随机数，不含任何个人身份信息；归因建立的是"匿名访问 ↔ 匿名设备"的弱关联
- 官网隐私声明需补一句："下载渠道与使用统计的匿名关联"

## 4. 方案 B：IP + 时间启发式归因（零客户端改动，兜底与存量回填）

- 对无票据设备：取 `firstSeen` 时刻的完整 IP（服务端上报时可见，仅展示掩码），在访客流水找「同 IP + firstSeen 前 7 天内」的访问，来源取该访问 rf 的分类
- NAT/公司网络会误归因 → 所有 B 归因标 `via: "heuristic"`，后台展示为「疑似来源」
- 存量设备（17 台 + 未来增长）可跑一次性批量回填脚本（`tools/backfill-origin-heuristic.php`，幂等）

## 5. 方案对比

| 维度 | 方案 A 第一层(服务端票) | 方案 A 第二层(客户端终身携带) | 方案 B(启发式) |
|---|---|---|---|
| 精度 | 精确（同 IP 前提） | 精确且抗换网络/清档重装 | 概率性 |
| 覆盖 | 官网渠道下载 | 官网渠道下载 | 全部设备(含第三方分发→只能标 unknown/疑似) |
| 客户端改动 | 零 | 小（随版本发版） | 零 |
| 服务端改动 | ticket.php + report 归因 | update/check 下发 tok | 批量回填脚本 |
| 上线节奏 | 可立即 | 随下个版本 | 可立即 |

**推荐组合**：一次性实现 A 第一层 + B（纯服务端）→ 后台立即见效；第二层随下个客户端版本发布，逐步把"疑似"升级为"精确"。

## 7. 风险与回滚

- 票据表膨胀 → 条数上限 + 过期清理（复用频控文件的清理模式）
- 误归因 → B 方案一律标 heuristic；A 层票据只在"IP 全等 + 7 天窗内"才精确消费，超窗补归因一律 confidence:"low"；tok 与 anonId 首绑锁定，防同 tok 多设备冒领（多设备走票据 attributed 数组）
- 回滚：各文件 `*.bak-origin-<日期>` 覆盖回去重新 deploy；票据表与 origin 字段可保留不清理（老代码自动忽略）
- 性能：report.php 每次多一次 isset 判断；票据匹配仅发生在新设备首报与 check 请求，量级 = 下载量，可忽略

## 8. 明确不做 / 待定

- 不做：第三方转载渠道的归因（无法覆盖，标 unknown）
- 待定：是否把 `origin` 打入升级包加密通道元数据（无必要，升级不归因）
- 待定：来源细分到具体仓库页/Release 页的粒度（第一期先到域名级）
